Dev Wrapped

“Spotify Wrapped” for any GitHub user. Type a username and get a short, animated story of their year on GitHub — the last 12 months or any calendar year — ending in a summary card you can download or share, which is also the link preview on LinkedIn and WhatsApp. Behind it is a small backend: a server-only GitHub client, a shared Redis cache with request coalescing, and per-IP rate limiting.

In one minute

The browser never talks to GitHub. A Server Component asks a Redis-backed cache for the user’s stats. On a miss, exactly one server request (it holds a Redis lock) calls GitHub with a secret token, turns the answer into plain numbers with pure functions, and saves them for everyone. The browser receives only those numbers, adds the one thing only it knows — its timezone — and plays the slides. A Route Handler draws the same summary as a 1200×630 PNG for sharing.

01  What it does

Nine full-screen slides with Instagram-style progress bars. Tap (left third goes back), arrow keys, Space, or on-screen buttons. Pick any year since the user joined GitHub from the intro slide, or add ?year=2024 to the URL.

#SlideWhere the number comes from
1Intro + year pickerGraphQL user { name avatarUrl createdAt }; availableYears()
2Total contributionscontributionCalendar.totalContributions for the chosen period
3Beyond the totalCommits, pull requests, code reviews and issues from contributionsCollection; totalStars() over the user’s repos
4Top 3 languageslanguageShares(): bytes per language over the 100 most-starred non-fork repos
5Busiest hour & weekdayHour: REST push events in the viewer’s timezone (hourHistogram()). Weekday: the daily calendar (busiestWeekday())
6Longest & current streaklongestStreak(), currentStreak(); “current” is hidden for a finished year
7Most-contributed repotopRepo() over commitContributionsByRepository
8Coder personalitypersonality(): the first matching rule wins
9Summary + Download / Share/api/card/[username]?year=&tz= PNG

Personality rules, in order: Night Owl (busiest hour 22:00–03:59), Early Bird (05:00–08:59), Weekend Warrior (over 35% of contributions on Saturday/Sunday), Streak Machine (longest streak of 30+ days), Polyglot (5+ languages over 5% each), otherwise Steady Builder.

Every state has its own screen: a loading skeleton, user not found, a “quiet year” story for users with no public activity, “GitHub needs a short break” (GitHub’s rate limit), “Slow down a little” (our own per-IP limit), and a retryable error page.

02  Architecture

Four places: the browser, the Next.js server on Vercel, Upstash Redis, and GitHub. Red lines are the only places a secret travels.

Only one server request at a time calls GitHub for a given user and period, and only on a Redis miss. The browser receives computed numbers and never sees a token.

03  The Redis cache, step by step

What lib/stats-cache.ts decides for every request. Most requests stop at step 1; only one request per user per hour reaches GitHub.

Tested with 10 simultaneous requests for a new user against the real Redis: 1 GitHub lookup (read from the rate-limit counter), and a repeat request in 36 ms.

04  One request, step by step

What happens when someone opens /torvalds?year=2024 for the first time.

  1. The browser requests the page. Next.js immediately streams app/[username]/loading.tsx, a skeleton shaped like the story, so the screen is never blank.
  2. page.tsx runs on the server. It reads ?year= with parseYear() (anything invalid means “last 12 months”) and the visitor’s IP with clientIdFrom(), then calls getWrappedStats(). React’s cache() makes generateMetadata and the page share that one call.
  3. lib/stats-cache.ts goes through the five steps above. On a miss it wins the Redis lock and checks the visitor’s rate limit.
  4. lib/github.ts sends one GraphQL query with from/to for 2024 (null for the last 12 months) and, only for the current period, up to 3 pages of the REST events API — in parallel with Promise.all. For a past year the events call is skipped, because GitHub only keeps about 30 days of events.
  5. Failed responses become typed errors: UserNotFoundError → notFound(); RateLimitError or TooManyRequestsError → the stale copy if there is one, otherwise a friendly screen rendered by page.tsx; anything else → error.tsx with Try again.
  6. computeStats() in lib/stats.ts turns the raw data into a plain WrappedStats object. It is saved in Redis for 24 hours and the lock is released.
  7. The page renders <Story stats={…} />, a Client Component, so the stats are serialized into the HTML and React hydrates it in the browser. The server also decides currentYear, so the browser’s first render matches exactly.
  8. In the browser, useTimeZone() reads the timezone (e.g. Asia/Kolkata); hourHistogram() and personalityFor() run there.
  9. On the last slide, Download links to /api/card/torvalds?year=2024&tz=Asia%2FKolkata. The route reuses the Redis entry, draws the card with next/og, and the CDN keeps the PNG for an hour. Link-preview bots get the same card without tz through the page’s og:image tag.

06  Design decisions and trade-offs

Green: clear win. Amber: a deliberate trade-off with a cost worth knowing.

Security

Secrets live only on the server

All GitHub calls are in lib/github.ts, which starts with import "server-only": if a Client Component ever imports it, the build fails. GITHUB_TOKEN and the Upstash token are not NEXT_PUBLIC_…, so Next.js never inlines them into browser JavaScript. The GitHub token is a fine-grained, read-only token for public data. Secrets live in .env.local (git-ignored) and Vercel’s environment variables, and the end-to-end tests deliberately blank the Redis variables so fake test data can never reach the real database.

Backend

A shared Redis cache with coalescing, stale fallback and rate limiting

Computed stats (a few KB) are cached, not raw GitHub responses, under wrapped:v2:{login}:{year}; the v2 is bumped when the stats shape changes, so old entries are simply ignored. The lock makes request coalescing work across every serverless instance, which an in-process Map could not. The rate limit only counts cache misses, so popular profiles cost nothing. When GitHub is down or rate-limited, the 24-hour stale copy is served instead of an error.

Upstash is used over HTTPS because serverless functions cannot keep a TCP connection pool. lib/store.ts hides it behind a five-method interface (get, set, setIfAbsent, deleteIfEquals, increment) with an in-memory twin, so tests and local runs use the same logic without Redis.

Trade-offs: a fixed window can allow a burst of up to 2× the limit across a window boundary; a sliding window is smoother but costs more Redis operations. Waiting requests poll every 250 ms; pub/sub would be faster but adds moving parts on a serverless platform.

Performance

Three more cache layers, each with its own job

React cache() dedupes work inside one request (page + metadata). Next.js’s data cache (revalidate: 3600) stores raw GitHub responses per deployment; the GraphQL POST with an Authorization header is still cached because revalidate is explicit, and the body is part of the key. The CDN keeps the PNG card with s-maxage=3600, stale-while-revalidate. The home page’s example links use prefetch={false}, because prefetching them made three GitHub lookups on every home page visit.

API design

One GraphQL query, and the year as a query parameter

GraphQL returns the calendar, contribution totals by type, repos, languages and stars in one round trip, so adding the “Beyond the total” slide cost no extra requests. The year is a filter on the same resource, so it is ?year=2024 rather than a new route: old links keep working and one page component serves both. parseYear() turns anything invalid into the default, and GitHub’s one-year limit on from/to is respected by construction (yearRange()).

Testability

All maths in pure functions

lib/stats.ts and lib/period.ts have no fetching, no clock and no randomness. Streaks across month and year boundaries, “today has no contributions yet”, ties (the earlier hour, weekday or repo wins), timezones including daylight saving time, and every personality rule plus their order are each tested with a few lines of input. The same functions run on the server, in the browser and in the card route.

Trade-off

The busiest hour uses the viewer’s timezone

The calendar is daily only, so hours come from push event timestamps, which are UTC. GitHub does not expose the coder’s timezone, so the hour is converted in the browser with Intl.DateTimeFormat and labelled “in your timezone”. The personality therefore depends on the viewer: the same push at 20:00 UTC is 01:30 in India (Night Owl) but 20:00 in London. useTimeZone() uses useSyncExternalStore with a null server snapshot, so there is no hydration mismatch.

Cost: the link preview (no viewer, so UTC) can show a different personality from the downloaded card (viewer’s timezone via ?tz=).

Sharing

The share card is generated, not screenshotted

new ImageResponse(<ShareCard />) turns JSX with inline flexbox styles into a PNG using Satori. The same URL is the page’s og:image, so a shared link previews as the card. Download is a same-origin <a download> with no JavaScript; Share uses navigator.share with a copy-link fallback. Satori supports only a subset of CSS, and every <div> with more than one child needs display: flex — including JSX text like @{login} · ….

Trade-off

Loading skeleton vs a real 404 status

loading.tsx streams the skeleton straight away, so the HTTP status (200) is sent before we know whether the user exists. The not-found UI replaces the skeleton and Next adds noindex, but the status stays 200. A true 404 would mean no skeleton, and people opening a shared link would see a blank screen for a second or two. The card API, which does not stream, returns a real 404.

Errors

Rate limits are handled in the page, not in error.tsx

In production, Next.js hides server error messages from error.tsx, so it cannot tell “rate limited” from “GitHub is down”. The page catches RateLimitError and TooManyRequestsError itself. GitHub reports limits two ways: REST uses 403/429 with x-ratelimit-remaining: 0; GraphQL usually answers 200 with errors[].type === "RATE_LIMITED".

Accessibility

Keyboard, screen reader and motion

Arrow keys and Space move slides (Space is ignored on focused buttons and links). A visible :focus-visible ring, labelled buttons, a real <select> for the year, an aria-live announcer (“Slide 4 of 9: Top languages”), and <dl> lists with the label before the value. useReducedMotion() sets animation duration to 0 and motion-safe: guards CSS animations. No auto-advance. h-dvh and safe-area padding for phones.

08  Known limitations

  • Busiest hour covers about 30 days, and past years have none: the public events API keeps at most 300 events from roughly the last month.
  • Viewer’s timezone, not the coder’s (see the trade-off above).
  • Public data only. Private contributions count only if the user shows them on their profile; private repos are not in languages or stars.
  • Organizations are not supported; GraphQL user(login:) returns NOT_FOUND for them.
  • 100 most-starred repos, top 10 languages each (no pagination yet).
  • One shared GitHub token: caching and coalescing stretch it far, but every visitor still shares one quota.
  • No request timeout on GitHub calls yet; a hanging call holds its lock until the lock expires (15 s).
  • Not-found returns HTTP 200 with noindex, because of streaming.

09  Roadmap and scale

ItemStatusWhy
Contribution breakdown and starsDoneRicher story from the same single query
Pick any yearDonePer-year cache keys, GraphQL date ranges
Redis cache, coalescing, stale fallback, rate limitingDoneThe GitHub quota, not CPU, is the bottleneck
Sign in with GitHub, sessions in RedisNextEach user spends their own quota; optional private stats (never put in the shared cache)
AI “year in one paragraph”NextStreamed LLM summary from the stats only, cached and rate-limited in Redis
Rate limiting at the edge (proxy.ts)LaterAbusive traffic never reaches a function
Timeouts and monitoringLaterAbortSignal.timeout(); track cache hit rate, GitHub quota left, p95 latency

“A million people open it on 31 December.” The servers scale on their own; what breaks first is the GitHub quota. The pieces already built answer most of it: a popular profile costs one GitHub call per hour thanks to the shared cache and coalescing, failures fall back to stale data, and per-IP limits stop scripts from burning the quota. What is left is spending users’ quota (sign-in), pre-warming the most-viewed profiles before the peak, and a queue with “ready in a few minutes” when the quota runs out.

Project overview · Next.js 16 · TypeScript

Dev Wrapped

“Spotify Wrapped” for any GitHub user: type a username and get a short, animated story of their last 12 months on GitHub, ending in a summary card that can be downloaded or shared, and that shows up as the link preview on LinkedIn and WhatsApp.

In one minute

The browser never talks to GitHub. A Server Component fetches the data with a secret token, caches it for an hour, turns it into plain numbers with pure functions, and sends only those numbers to the browser. The browser adds the one thing only it knows — its timezone — to work out the busiest hour and the personality, and plays the slides. A Route Handler draws the same summary as a 1200×630 PNG for sharing.

01  What it does

Nine full-screen slides with Instagram-style progress bars. Tap (left third goes back), arrow keys, Space, or on-screen buttons.

Personality rules, in order: Night Owl (busiest hour 22:00–03:59), Early Bird (05:00–08:59), Weekend Warrior (more than 35% of contributions on Saturday/Sunday), Streak Machine (longest streak of 30+ days), Polyglot (5+ languages over 5% each), otherwise Steady Builder. A user with no public contributions gets a short “quiet year” story instead.

02  Architecture

Three places code runs: the browser, the Next.js server on Vercel, and GitHub. The red line is the only place the token exists.

Only the data cache talks to GitHub, and only on a cache miss. The browser receives computed numbers and never sees the token.

03  One request, step by step

What happens when someone opens /torvalds for the first time this hour.

  1. The browser requests /torvalds. Next.js immediately streams app/[username]/loading.tsx (a skeleton shaped like the story) so the screen is never blank.
  2. app/[username]/page.tsx runs on the server and calls getWrappedStats("torvalds") in lib/wrapped.ts. It is wrapped in React’s cache(), so generateMetadata and the page share one call.
  3. lib/github.ts checks the username format, then sends two requests in parallel (Promise.all): one GraphQL query for the calendar, repos and languages, and the REST events API (up to 3 pages of 100) for push timestamps.
  4. Each fetch goes through the Next.js data cache with revalidate: 3600. On a miss it calls GitHub with the token; on a hit (the next hour) GitHub is not called at all. Measured locally: 1.7 s on a miss, about 50 ms on a hit.
  5. Failed responses become typed errors: UserNotFoundError → notFound() → not-found.tsx; RateLimitError → a “GitHub needs a short break” screen rendered by the page; anything else → error.tsx with a Try again button.
  6. computeStats() in lib/stats.ts turns the raw data into a plain WrappedStats object. Push times stay raw, because the hour depends on the viewer.
  7. The page renders <Story stats={…} />. That is the boundary: Story.tsx is a Client Component, so the stats are serialized into the page and React hydrates it in the browser.
  8. In the browser, useTimeZone() reads Intl.DateTimeFormat().resolvedOptions().timeZone (e.g. Asia/Kolkata). hourHistogram() and personalityFor() run there. The user moves through the slides.
  9. On the last slide, Download is a plain link to /api/card/torvalds?tz=Asia%2FKolkata. The route reuses the cached data, draws the card with next/og, and the CDN keeps the PNG for an hour. Link-preview bots get the same URL without tz through the page’s og:image tag.

05  Design decisions and trade-offs

Green: clear win. Amber: a deliberate trade-off with a cost worth knowing.

Security

The token lives only on the server

All GitHub calls are in lib/github.ts, which starts with import "server-only": if any Client Component ever imports it, the build fails. The variable is GITHUB_TOKEN, not NEXT_PUBLIC_…, so Next.js never inlines it into browser JavaScript. It is a fine-grained token with read-only access to public data, stored in .env.local (git-ignored) and in Vercel’s environment variables.

Trade-off: every request goes through our server, so our server is the bottleneck and our token’s rate limit is shared by all users. Caching (next card) is what makes this OK.

Performance

Cache GitHub for an hour, at two levels

With a token, GitHub allows 5,000 REST requests per hour, and a separate points budget for GraphQL. One new user costs 1 GraphQL query plus 1–3 REST pages. fetch(…, { next: { revalidate: 3600 } }) stores responses in the Next.js data cache, so a popular profile costs GitHub nothing after the first view each hour. Usernames are lowercased so /Torvalds and /torvalds share one entry. The PNG adds Cache-Control: s-maxage=3600, stale-while-revalidate=86400 so the CDN serves it without running our code.

Trade-off: stats can be up to an hour old. For a yearly summary that is invisible. The home page’s example links have prefetch={false}, because prefetching them made three GitHub lookups on every home page visit.

Testability

All maths in pure functions

lib/stats.ts has no fetching, no clock and no randomness. Raw data goes in, numbers come out, so each rule can be tested with a few lines of input: streaks across month and year boundaries, “today has no contributions yet”, ties (the earlier hour, weekday or repo wins so results never change), timezones including daylight saving time, and every personality rule plus their order. The same functions run on the server (stats), in the browser (hour, personality) and in the card route.

Trade-off

The busiest hour uses the viewer’s timezone

The contribution calendar is daily only, so hours come from push event timestamps, which are UTC. GitHub does not expose the coder’s timezone, so the hour is converted in the browser with Intl.DateTimeFormat and labelled “in your timezone”. Because the personality depends on the hour, it depends on the viewer too: the same push at 20:00 UTC is 01:30 in India (Night Owl) but 20:00 in London.

useTimeZone() uses useSyncExternalStore with a server snapshot of null, so the server HTML and the first browser render match (no hydration error) and the real value appears right after.

Cost: the link preview (no viewer, so UTC) can show a different personality from the downloaded card (viewer’s timezone, sent as ?tz=). validTimeZone() falls back to UTC for invalid values.

Sharing

The share card is generated, not screenshotted

app/api/card/[username]/route.tsx returns new ImageResponse(<ShareCard />). next/og uses Satori to turn JSX with inline flexbox styles into SVG, then into a PNG. The same URL is the page’s og:image and twitter:image, so a shared link previews as the card. Download is a same-origin <a download>, so it needs no JavaScript. Share uses the phone’s share sheet (navigator.share) and falls back to copying the link.

Gotchas learned: Satori supports only a subset of CSS (no grid, no Tailwind classes), and every <div> with more than one child needs display: flex. That includes JSX text like @{login} · …, which is several text nodes, so those are written as a single template string.

Trade-off

Loading skeleton vs. a real 404 status

loading.tsx makes Next.js stream the skeleton straight away, so the HTTP status (200) is sent before we know whether the user exists. When the page later calls notFound(), the not-found UI replaces the skeleton and Next adds <meta name="robots" content="noindex">, but the status stays 200.

Why I kept it: the alternative, a true 404 status, means no skeleton, so someone opening a shared link would stare at a blank screen for 1–2 seconds. noindex keeps search engines correct anyway.

Errors

Rate limits are handled in the page, not in error.tsx

In production, Next.js replaces server error messages with a generic one before they reach error.tsx, to avoid leaking secrets. So error.tsx cannot tell “rate limited” from “GitHub is down”. The page catches RateLimitError itself and renders its own screen. Rate limits are detected two ways: REST uses HTTP 403/429 with x-ratelimit-remaining: 0, while GraphQL usually answers 200 with errors[].type === "RATE_LIMITED".

Testing

A fake GitHub for end-to-end tests

GitHub is called from the server, so browser-level mocking cannot see those calls. lib/github.ts reads GITHUB_API_URL (default https://api.github.com), and Playwright starts e2e/mock-github.mjs, a small Node HTTP server with four users: normal, no activity, rate-limited, and not found. The tests run the real production build on a Pixel 7 profile in the Asia/Kolkata timezone, so the timezone logic is tested end to end. CI needs no token and no network access to GitHub.

Accessibility

Keyboard, screen reader and motion

Arrow keys and Space move slides; Space is ignored when a button or link has focus so it does not fire twice. A visible :focus-visible ring, labelled previous/next buttons, an aria-live region announcing “Slide 4 of 9: Top languages”, and aria-roledescription carousel/slide. useReducedMotion() sets animation duration to 0, and Tailwind’s motion-safe: guards the progress bars and skeleton pulse. No auto-advance, so nobody is rushed. On phones, h-dvh and safe-area padding keep controls clear of the address bar and the notch.

06  Known limitations

  • Busiest hour covers about 30 days. The public events API returns at most 300 events and, as measured, only about the last 30 days, not the full year. The slide says so.
  • Viewer’s timezone, not the coder’s. See the trade-off above.
  • Public data only. Private contributions appear in the total only if the user chose to show them on their profile; private repos are not in languages or the top repo.
  • Organizations are not supported. GraphQL user(login:) returns NOT_FOUND for them, which shows the not-found page.
  • 100 most-starred repos, top 10 languages each. Languages and stars are measured on a user’s 100 most-starred non-fork repos (no pagination yet).
  • One shared token. Every visitor uses the same GitHub rate limit; caching makes this fine for a portfolio, not for a viral launch (next section).
  • Not-found returns HTTP 200 with noindex, because of streaming (see above).

07  What I would do next at scale

“What if a million people open it on 31 December?”

  • The real bottleneck is GitHub, not our servers. One token allows about 5,000 REST requests an hour. Vercel can scale the Next.js functions, but a million new users would need about a million GraphQL calls. So the answer is about GitHub quota, not CPU.
  • Use each user’s own quota. Add “Sign in with GitHub” (OAuth or a GitHub App). Requests for your own Wrapped then use your token’s limit, and a GitHub App’s limit also grows with installations.
  • Shared cache. Move from the per-deployment data cache to a shared store (Redis / Vercel KV) keyed by lowercase username with a 1–24 hour TTL, and cache the computed stats (a few KB) rather than raw responses.
  • Request coalescing. If 10,000 people open /torvalds in the same second on a cold cache, make only one GitHub call and let the rest wait for it (a lock or “single flight” per username).
  • Pre-compute for the peak. Before 31 December, warm the cache for the most-viewed profiles in a background job. Serve slightly stale data (stale-while-revalidate) instead of failing.
  • A queue when the budget runs out. When GitHub quota is exhausted, put new users in a queue and show “we’ll be ready in a few minutes”, instead of an error.
  • Protect the budget. Rate-limit by IP at the edge, so one script cannot burn the quota by requesting random usernames. Cache “not found” answers briefly too.
  • Share images. Already CDN-cached. At scale, store generated PNGs in object storage (e.g. Vercel Blob or S3) keyed by username, date and timezone.
  • Observability. Track cache hit rate, GitHub remaining quota (from response headers), p95 latency and error rate, and alert before the quota runs out.
